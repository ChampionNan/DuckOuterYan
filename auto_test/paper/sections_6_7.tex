\section{Optimization}
\label{sec:optimization}

OuterYan compares two alternatives: DuckDB's normally optimized plan and a
reordered plan with semi-join reduction. It first estimates the reduction,
then chooses a join order for the reduced inputs, and finally checks whether
the expected join savings justify the reduction overhead.

\subsection{Cost Model}
\label{sec:cost-model}

We score a join tree by the sum of its estimated intermediate cardinalities:
\begin{equation}
 C_{\mathrm{out}}(T)=\sum_{\text{join }v\in T}\widehat{N}(v).
 \label{eq:cout}
\end{equation}
A leaf contributes zero cost. For an outer join, the output includes both
matching tuples and unmatched tuples from its preserved sides. The default
model assigns unit weight to each output tuple. These costs are row-work
estimates, not predictions of elapsed seconds.

Let $T_D$ denote the normally optimized DuckDB plan and $T_Y$ the OuterYan
candidate. We compare
\begin{equation}
 \begin{aligned}
 C_D &= C_{\mathrm{out}}(T_D),\\
 C_Y &= C_{\mathrm{out}}(T_Y)+\lambda C_{\mathrm{SJ}},
 \end{aligned}
 \label{eq:plan-costs}
\end{equation}
where $C_{\mathrm{SJ}}$ accounts for both reduction rounds and $\lambda=1$
in the evaluated configuration. Both plans use the same scoring function;
the baseline is not the unoptimized input tree. The reduction schedule is
fixed before join enumeration, so its cost is added once to the complete
candidate rather than to every dynamic-programming state.

\subsection{Cardinality Estimation}
\label{sec:cardinality-estimation}

For a join with input sizes $N_L,N_R$, let $d_L,d_R$ be the estimated numbers
of distinct join keys, bounded between one and the corresponding nonempty
input size. Composite-key estimates multiply the per-column distinct counts
under an independence assumption. Statistics remain local to each original
join edge: we do not propagate transitive equalities across outer joins.

Assuming uniform key frequencies and containment of the smaller key domain
in the larger one, we estimate the matching output $M$ and unmatched tuples
$U_L,U_R$ as
\begin{equation}
 \begin{aligned}
 M   &= \frac{N_LN_R}{\max(d_L,d_R)},\\
 U_L &= N_L\max(0,1-d_R/d_L),\\
 U_R &= N_R\max(0,1-d_L/d_R).
 \end{aligned}
 \label{eq:join-cardinality}
\end{equation}
An inner join returns $M$; a left, right, or full outer join additionally
returns $U_L$, $U_R$, or both, respectively. Empty inputs are handled directly
using the join semantics. Swapping the children also swaps LEFT and RIGHT,
so the same logical input remains preserved.

\subsection{Reduction and Plan Enumeration}
\label{sec:two-round-reduction}
\label{sec:plan-enumeration}

Reduction follows preservation semantics. An inner edge permits filtering
in both directions. A one-sided outer edge permits only the preserved side
to filter the non-preserved side; a full outer edge permits neither.
Provably redundant reductions are omitted. The complete bottom-up round
precedes the top-down round, and each step uses the estimates updated by
earlier steps.

For a filter built on $b$ and applied to $p$, we scale each edge-local
distinct count by that relation's retained fraction, with a floor of one
for a nonempty input. Using these updated distinct counts, the estimated
probe size becomes
\begin{equation}
 N'_p=N_p\min(1,d_b/d_p).
 \label{eq:semijoin-update}
\end{equation}
An empty build removes all probe tuples; an empty probe remains empty.
With unit row-work weights, the reduction cost is
\begin{equation}
 C_{\mathrm{SJ}}
 =\sum_{\text{new filters}}3N_b
  +\sum_{\text{probe steps}}(N_p+N'_p).
 \label{eq:semijoin-cost}
\end{equation}
The three build terms represent materialization, filter construction, and
replay. Probe work includes one lookup per input tuple and emission of the
survivors. Reusing a filter does not charge its build work again.

The final reduced sizes initialize the enumeration leaves. After rewriting
the join expression into an associative form, dynamic programming combines
connected relation subsets and retains the cheapest tree for each subset.
A combination costs the two child plans plus the estimated output of their
join, as in Equation~\ref{eq:cout}. Edge types and predicate orientation are
preserved, and cross products are never introduced. Output-root preferences
are tried where applicable; if they prevent a complete plan, the search
retries without that preference. For 12 or more relations, or after the
10,000-pair search budget is exhausted, a greedy search repeatedly merges
the cheapest connected pair.

For an all-inner tree with reductions in both directions on every edge,
the estimated output of a connected subplan is bounded below by its largest
reduced leaf. This prevents the uniform-key estimator from predicting fewer
tuples than full reduction allows. The correction is not applied to general
outer-join trees.

\subsection{Candidate Selection}
\label{sec:plan-selection}

We first compare the candidates' join groupings using the sets of stable
base-relation instances below their join nodes. This comparison ignores
join type, child orientation, and semi-join wrappers. If the groupings are
identical, DuckDB's plan is retained. A missing candidate, invalid cost
comparison, or proof that the baseline eliminates all join work also keeps
the baseline.

For a genuinely different grouping, the default gate requires $C_Y\leq C_D$.
If the reductions retain less than 90\% of the estimated input tuples in
total, the stricter condition $C_Y\leq0.90C_D$ requires additional headroom.
When a table filter uses a generic selectivity estimate, both candidates
are also rescored without that estimated filter reduction, and the scenario
with the larger candidate-to-baseline cost ratio governs selection.
An additional guard rejects a candidate that retains at least 99\% of its
input when the largest estimated input is at least 1,000 times the smallest
unfiltered base relation with such an uncertain filter.

A narrowly scoped stretch gate permits $C_Y\leq1.20C_D$ only when the
candidate's real-join cost is lower, its summed real-join input cardinality
is at most 30\% of the baseline's, and the reductions retain at least 95\%
of the input tuples. This gate is unavailable when the generic-filter
check, amplification guard, or full-reduction lower-bound correction is
active. Thus, the relaxed threshold targets benefits from regrouping, not
candidates that rely on aggressive reduction estimates. These thresholds
are fixed implementation parameters in the evaluated V7 policy; they are
heuristics, not guarantees of a runtime improvement.

\section{Experiments}
\label{sec:experiments}

We evaluate \emph{DuckOuterYan}, our integration of OuterYan into DuckDB,
using 32 worker threads. We report the performance of enabling the optimizer
over the complete measured workload, then examine selected plans and their
execution phases.

\subsection{DuckOuterYan System Design}
\label{sec:system-design}

DuckOuterYan integrates plan generation, selection, and execution into
DuckDB's existing vectorized engine. The optimizer operates after filter
pushdown and builds both alternatives from the same logical input. One
copy follows DuckDB's native outer-join simplification and join-order
optimization. The other is converted into an operator-tree representation
that records relation identities, equality predicates, and preservation
directions.

The OuterYan path simplifies outer joins where null rejection permits,
records the legal two-round reduction schedule, and rewrites join types
into an associative form for enumeration. Recording reductions before this
rewrite keeps their semantics independent of the subsequently chosen
grouping. After the cost comparison in Section~\ref{sec:optimization}, a
selected candidate is resimplified and lowered back to DuckDB operators;
otherwise the native alternative continues through the normal optimizer.
The active path handles eligible acyclic equality-join queries. Unsupported
queries, including queries containing aggregation or DISTINCT, use the
native optimizer.

At execution time, semi-join build operators materialize their input and
construct reusable membership filters. Probe operators filter DuckDB
\texttt{DataChunk}s without adding output columns or changing surviving
tuple multiplicities. Eligible bounded integer keys use a bitmap; other
keys, or ranges exceeding the per-filter memory budget, use a hash filter.
Pipeline dependencies prevent a probe from starting before its filter is
finalized and preserve the bottom-up/top-down phase boundary. The remaining
joins and result production use DuckDB's execution engine. Profiling
attributes work to the two reduction rounds, subsequent joins, and other
operators separately.

\subsection{Outer-Join Benchmark}
\label{sec:outerjoin-benchmark}

We derive a controlled structural workload from TPC-H~\cite{tpch},
TPC-DS~\cite{tpcds}, JOB~\cite{job}, and SQLStorm~\cite{sqlstorm25}.
Its 34 traceable source patterns comprise 5 TPC-H, 7 TPC-DS, 10 JOB, and
12 SQLStorm queries. Each source contributes a connected acyclic join graph
with three to six relation instances. We retain the relation instances and
equality edges, but treat each generated expression as an independently
specified query; regrouped outer joins are not claimed to be semantically
equivalent to the complete source query or to one another.

Each source pattern contributes exactly five predetermined input expressions.
These include left-deep and right-deep traversals and, where the graph permits,
two connected bushy groupings. An unavailable bushy slot is replaced by a
predeclared mixed or secondary right-deep control rather than by an artificial
cross product. The resulting 170-query structural layout contains 46
left-deep, 80 right-deep, and 44 bushy inputs. Join labels are assigned by a
deterministic blocked rotation over INNER, LEFT, RIGHT, and FULL, independently
of measured runtime. Across the 625 join-edge occurrences, there are 157 INNER
and 156 each LEFT, RIGHT, and FULL labels. A query with at least four edges
contains all four kinds; shorter queries contain mixed two- or three-kind
slices. Thus the workload includes both all-outer expressions using multiple
outer-join kinds and expressions that combine INNER with outer joins, with no
single-kind query.

A separate 54-query evaluation component contains nine industry-inspired
integration patterns, all 25 completed Graph-generator patterns, and 20
schema-synthetic optimizer-stress guards. Graph membership is complete rather
than selected from historical performance; seven Graph rows retain old
speed-ups only as provenance. The Graph expressions cover 10 bushy, seven
left-deep, and eight right-deep trees. The schema-synthetic guards remain
explicitly labeled and are not presented as an unbiased source-derived
workload. The active v1 union contains 224 unique queries: all 170 structural
queries and all 54 controls. Timeout observations from the retired FULL-heavy revision are not
reused because changing a join label changes the query semantics and plan
space. Consequently, no query is excluded before mixed-v1 is measured.
Across the complete v1 union, the 801 input join-edge occurrences contain 200
INNER, 201 LEFT, 200 RIGHT, and 200 FULL labels; 32 queries use only multiple
outer-join kinds and 192 combine INNER with outer joins.

V2 keeps the same 34 source graphs, five structural slots per source, and mixed
join vectors as v1. The balance also
holds within source-family/shape strata to within three edge occurrences. A
query with at least four join edges contains all four kinds; shorter queries
receive mixed two- or three-kind slices. Thus V2 includes both queries composed
entirely of outer joins (using multiple kinds among LEFT, RIGHT, and FULL) and
queries that combine INNER and outer joins, while avoiding an all-FULL-dominated
workload. Relations and equality edges remain those of the corresponding
TPC-H, TPC-DS, JOB, or SQLStorm source pattern; no measured speedup is used to
choose the vectors. These counts describe join labels in the input expression;
the optimizer may subsequently simplify a label or select a different physical
join implementation.

Every V2 base is instantiated at three deterministic hash-sampling levels,
targeting approximately $0.1\%$, $1\%$, and $5\%$ of the source-derived anchor
domain. A base retains the same join vector at all three levels, and each tier
contains the same 170 structures---46 left-deep, 80 right-deep, and 44
bushy---so neither selectivity nor shape is confounded with join type. All 54
Graph, industry, and schema-synthetic evaluation controls remain separate
control strata. We preserve their relation graph and parentheses but relabel
their join edges with the same deterministic balancing objective. The complete
564-query V2 workload has 512 INNER, 513 LEFT, 513 RIGHT, and 513 FULL edge
occurrences; 75 queries use only outer joins and 489 also contain INNER.

We additionally define a separate V3 wide-range selectivity ablation. Six
mixed, source-derived counterparts of feasibility-screened v1 structures with
at least four relations are selected from static metadata, without consulting
measured speed: two each from TPC-H, TPC-DS, and JOB, and two each of
left-deep, right-deep, and bushy shape across the complete set. Each execution
family contributes one native benchmark source and one SQLStorm-derived
source, retaining provenance from TPC-H, TPC-DS, JOB, and SQLStorm. Each base is
instantiated at $0.025\%$, $0.05\%$, $0.2\%$, $10\%$, $20\%$, $50\%$, and
$80\%$, yielding 42 queries with six queries per tier.
The shared 4,000-bucket hash partition makes these samples deterministic and
nested. Equal tier counts do not imply uniformly spaced numeric selectivities
or identical realized cardinalities. Because variants of the same base are
correlated, this ablation is reported separately from the 564-query main
workload.

The September 16 results used a retired FULL-heavy corpus revision and are not
results for the mixed workload described here. V1, V2, V3, and the wide-range
ablation require fresh complete runs; no performance statistic is inferred
from corpus membership alone.
SQLStorm-derived queries are assigned to the family of their underlying schema.

\subsection{Experimental Setup}
\label{sec:experimental-setup}

\paragraph{Environment and data.}
The reported server has an Intel Xeon Silver 4116 at 2.10\,GHz, 24 physical
cores, 48 hardware threads, and 192\,GB RAM. We use a release build of the
DuckDB-based research fork and set \texttt{threads=32} for both configurations.
TPC-H and TPC-DS use scale factor 100. JOB uses the local IMDb/JOB database,
and the graph relations are built from the SNAP Bitcoin Alpha edge list.
% VERIFY before submission: OS, tested commit, compiler, storage, memory/spill
% settings, and exact JOB/graph snapshots are not recoverable from the CSV.

\paragraph{Compared configurations.}
\emph{DuckDB} disables only the \texttt{outer\_yan} optimizer.
\emph{DuckOuterYan} enables the V7 gated policy while leaving the remaining
DuckDB settings unchanged. Enabling the optimizer does not force its candidate:
the ON configuration may retain DuckDB's native plan.

\paragraph{Timing and profiling.}
Following the warm-cache, median-of-repetitions measurement principle used by
Yannakakis+, each configuration first executes one unmeasured warm-up and then
three measured executions. We report the median wall-clock time of the three
measured executions. Each OFF or ON batch uses a fresh DuckDB CLI process.
The timer covers optimization, execution, and complete result consumption, but
excludes process startup and session-setting commands. Trash-output mode avoids
terminal formatting and result-file I/O. We do not flush the operating-system
cache between repetitions; the measured executions therefore follow a warm-up.
Profiling is disabled during these runtime measurements.

For queries whose ON execution selects OuterYan, we run a separate profiled ON
batch with the same one-warm-up plus three-measurement protocol. The reported
phase tuple is taken from the complete measured profile whose wall latency is
the median. This keeps Round~1, Round~2, Round~3, Other, CPU total, and wall
latency from one execution rather than combining independently selected
medians. Phase components are accumulated operator CPU work across threads and
sum to profile CPU time; they are not an additive decomposition of wall time.

\paragraph{Reported metrics.}
For query $q$, speed-up is
$S_q=T_{\mathrm{DuckDB},q}/T_{\mathrm{DuckOuterYan},q}$.
We report the geometric mean
$\exp\!\left(\frac{1}{n}\sum_q \log S_q\right)$, which weights queries equally
in log space, and the total-time ratio
$\sum_q T_{\mathrm{DuckDB},q}/\sum_q T_{\mathrm{DuckOuterYan},q}$, which weights
queries by elapsed time. All correct finite timing pairs are retained,
including regressions and native-plan fallbacks. The representative phase
figure is only a display sample and is never used to compute population tables.
